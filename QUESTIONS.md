Slider ranges and defaults in 7.2 are unchanged. FYI to CTO. |
| 4 | developer 1 (WP5) | Design 6.5.4 lets `combinedSlipCoupling` below 1 produce a resultant tire force above `mu_eff*Fz` (about 1.41x at coupling 0), which contradicts the unit test specified in 13.1 ("friction ellipse never returns a combined force larger than mu_eff*Fz"). | PM decision 2026-09-20: the FORMULA is right and the 13.1 test sentence is wrong. 6.5.4 intends coupling as a forgiveness dial and explicitly calls coupling 0 "independent" and "less believable". Keep the formula; test the ellipse the formula defines at any coupling; assert the strict circle only at coupling = 1; add a coupling 0 test pinning independent axes so it is not later "fixed". |
| 5 | developer 1 (WP5) | Design 6.2 prints front mass share as `0.5 - comLongOffset / wheelbase`, but 6.2 and 7.2 both define positive `comLongOffset` as moving weight FORWARD (more understeer), which requires front share to increase. | PM decision 2026-09-20: the printed minus is an error; implement `0.5 + comLongOffset / wheelbase` and unit-test that positive offset increases front static load. Left as printed it would silently invert the understeer/oversteer slider and make the human tuning session actively misleading. |
| 6 | developer 1 (WP5) | Design 6.10 impulse limiting (`|F|*dt <= m_wheel*|v_slip|`) applied to all tire forces would forbid launching from rest, since slip velocity is zero at standstill so the cap is zero. | PM decision 2026-09-20: apply the cap only to DISSIPATIVE forces that oppose an existing slip velocity (lateral tire force, braking, handbrake), never to engine drive force. The cap exists to stop friction overshooting and oscillating at low speed and high stiffness; drive force is what creates slip, so capping it by current slip is circular. |
| 7 | developer 1 (WP5) | Design 6.8 D (air damping) and 6.8 E (anti-flip) are internal constants, but acceptance criterion 6 says all assists can be set to zero. Proposal was to scale both by `yawAssist`. | PM decision 2026-09-20: REJECTED the yawAssist coupling; keep D and E as internal constants per 6.8 E. Overloading `yawAssist` would mean a tuner lowering it for drift character silently loses flip recovery, with nothing in the UI explaining why. "All assists to zero" means the tunable HANDLING assists (`countersteerAssist`, `yawAssist`, and the yawAssist-gated drift limiter). D acts only with fewer than 2 wheels grounded and E only past 35 deg roll; neither occurs in normal flat-pavement driving, so neither masks the raw tire model. Required a unit test proving zero assist yaw torque while grounded at `countersteerAssist = 0` and `yawAssist = 0`. |
| 8 | developer 1 (WP5) | Should the boost meter start empty and charge only through drifting? | PM decision 2026-09-20: yes, per the 6.9 reward loop. But this is a tuning lab, so tuning boost parameters must not require executing a drift first: the drift meter must be directly settable through the `window.__game` test surface, plus a debug hotkey if cheap. |
| 9 | PM (found in review) | Two independent mass-rebuild paths existed on main after WP7: `src/main.ts` applied `needsRebuild` changes immediately while `src/ui/tuningSession.ts` ran its own 100 ms debounced rebuild, so one slider change rebuilt mass properties twice and the paths could interleave. | PM decision 2026-09-20: developer 1 owns a SINGLE debounced applier in the boot path with `flush()` and `cancel()`. The Options panel stops applying rebuilds and only DISPLAYS rebuild state (idle/pending/error/unavailable) reported to it, keeping the D3 pending-mass-update marker working. Chosen because boot is the only path present in headless runs (perf harness, e2e, scripted input), so one code path serves both mounted and unmounted cases. |
